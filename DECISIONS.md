# Build Decisions & Architectural Guide

This file captures the build decisions made during planning and development. It supplements the
requirements in `Coding Agent Prompt — Versa Telecom Credential Manager MVP.md`. Record any
significant architectural change or expansion here before implementing it.

---

## 1. Technology Stack Decisions

### 1.1 UI Framework — Ant Design (antd)

We chose **Ant Design** for the management interface. Rationale:

- Enterprise-grade component library with mature, professional Data Tables (critical for a
  3,000+ row CPE inventory).
- Built-in responsive breakpoints suitable for phone and laptop field-engineer workflows.
- Well-maintained TypeScript definitions.
- Established enterprise adoption and documentation.

Stack: React 19 + TypeScript, Vite, Zustand (state), React Router (routing), Axios (HTTP),
Ant Design 6.

### 1.2 Identity & Access — Keycloak (self-hosted)

We chose **Keycloak** as the authentication/authorisation broker. Rationale:

- Directly supports the requested **LDAP/Active Directory user federation** (validates passwords
  against AD, syncs users/groups without ever importing passwords).
- Provides OIDC/OAuth 2.0 endpoints the FastAPI backend can validate locally via JWKS.
- Self-hosted (matches "on-premise / corporate LAN" deployment), free, and widely used.
- Roles (`admin`, `security_operator`, `field_engineer`) live in Keycloak and are mapped from /
  to AD groups in production.

LDAP federation is configured with placeholders for the connection URL / bind DN / users DN.
The real values will be filled during the LDAP integration phase once the AD OU structure is
supplied. Development uses a bundled mock OpenLDAP service.

Design intent: the application **never** stores its own passwords. Authentication identity lives
in Keycloak + AD. The app trusts validated Keycloak JWT claims for RBAC.

### 1.3 Protocol — OIDC / OAuth 2.0

- Backend validates access tokens locally against Keycloak's JWKS endpoint (no round-trip per
  request).
- Token claims (`realm_access`.roles / `resource_access`.<client>.roles) drive RBAC.
- No secrets are stored in JWTs.

### 1.4 Reverse Proxy — nginx (inside the stack)

Per user decision, nginx is part of the Docker stack. It:

- Terminates TLS (self-signed cert now, Corporate PKI later).
- Routes `/` -> frontend, `/api/` -> backend, `/auth/` -> Keycloak.
- Applies rate limiting on sensitive/auth endpoints.
- Sets security headers (CSP, X-Frame-Options, HSTS-ready, etc.).

Self-signed certificates are generated by `scripts/generate-certs.sh`. Corporate PKI
replacement is a later operational step (swap cert files, no code change).

### 1.5 Deployment Model — Full Docker Compose

- Single `docker compose up` runs the whole MVP for local development.
- Services: nginx, frontend, backend (FastAPI), Keycloak, PostgreSQL, Redis, mock OpenLDAP
  (dev profile).
- Networks: `frontend-net` (exposed), `backend-net` (internal), `ldap-net` (external, for AD).
- Production: same compose file, with environment-specific `.env`, HTTPS via nginx, and the
  mock LDAP profile disabled.

### 1.6 Backend — Python / FastAPI

- FastAPI + SQLAlchemy 2 + Alembic migrations + Pydantic v2 + PostgreSQL.
- Redis used for rate-limit/state where applicable.
- Secret storage abstracted behind a `SecretStore` interface
  (see section 3). Development implementation only — never a plaintext DB implementation.

### 1.7 Versa Integration — Multi-Version Support (22.1.3 and 22.1.4)

The estate runs **both Versa Director 22.1.3 and 22.1.4**. Verified facts:

- Both releases are pre-23.1.1, so they share the **same Northbound REST API protocol**:
  - Port 9182 — HTTP Basic auth.
  - Port 9183 — OAuth token (`POST /auth/token` with client_id/client_secret/username/password).
- Candidate credential-change operations (TO VERIFY in lab):
  - `POST /vnms/users/user/change-password` (User Management API)
  - `POST /vnms/secure/access/localuser/password` (Secure Access API, requires `regtoken`)
- Swagger per release: `https://<director>:9182/docs/swagger-ui.html`

Design:
- One `VersaDirectorPre23Client` implementation covers both 22.1.3 and 22.1.4.
- A `Director` entity stores per-node identity including `versa_version` and a capability flags
  object (per-operation support matrix).
- `versa_client` factory selects implementation from `versa_version`.
- A version-compatibility matrix lives in `docs/versa-version-matrix.md`; nothing is marked
  verified until tested in the lab against both versions.
- Real credential-change remains **TODO** until the mechanism is confirmed on the exact
  releases. Mock provider is used everywhere until then.

## 2. Roles & RBAC

Roles (defined in Keycloak realm).

| Role             | Capabilities |
|------------------|--------------|
| `admin`          | Manage CPE inventory, initiate rotation, view audit, manage app configuration |
| `security_operator` | View CPEs, initiate rotations, view audit events |
| `field_engineer` | View authorised CPEs, request credential access for authorised devices |

Server-side RBAC via FastAPI dependencies reading Keycloak token roles. No unrestricted CPE
access. MVP authorisation model: simple user-to-CPE assignment (region/site/team expansion is a
future enhancement).

---

## 3. Secret Storage Abstraction

Interface: `SecretStore` with `create_secret`, `get_secret`, `update_secret`, `delete_secret`,
`rotate_secret`.

- Development implementation: `MockVaultStore` (in-memory, encrypted-at-rest, labelled
  DEV-ONLY, NOT a plaintext DB implementation).
- Production candidates (future): Telecom vault, CyberArk, HSM/KMS-backed KMS.
- The database stores only `secret_reference`, never the credential value.
- Design allows CyberArk to be integrated later without changing application architecture.

Selection is driven by config: `SECRET_STORE_TYPE` (e.g. `mock_vault`).

---

## 4. DB Model (initial)

Entities: `User`, `Role`, `Director`, `CPE`, `Credential`, `AccessRequest`, `AuditEvent`,
`TicketReference`. Key entities:

- `users` (mirror of Keycloak identity, no passwords stored).
- `directors` (per-VD node, includes `versa_version`, API base URL, capability flags; OAuth
  client secret held in SecretStore by reference).
- `cpes` (identity, site, serial, mgmt IP, director ref, status, last_seen).
- `credential_versions` (username, `secret_reference`, version, status, timestamps).
- `audit_events` (append-oriented; no update/delete for normal users).
- `cpe_assignments` (MVP user-to-CPE assignment for field engineer authorisation).

CPE table must support >= 5,000 records without architectural change (indexes, pagination).

---

## 5. Audit Logging

Every sensitive operation emits an `AuditEvent` (timestamp, user, role, action, CPE, ticket,
reason, source IP, user-agent, success/failure, correlation ID). Never records the secret.
Action vocabulary follows the requirement document (e.g. `CREDENTIAL_VIEW_REQUESTED`,
`CREDENTIAL_ROTATION_SUCCEEDED`, `ACCESS_DENIED`).
